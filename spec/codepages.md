# cc:Mail character sets and code pages

How cc:Mail messages record the code page of their text, the CCINTL.TB code page data file, and
how our server converts text. This file covers the character set rules only. General SMTP and
POP3/IMAP mapping is in `smtp-link.md` and `pop3-imap.md`.

## 0. Notation and code page numbers

Tags in this file are hex (tag 0x21 = 33, tag 0x15 = 21). `TB+x` is offset x in CCINTL.TB (the
code page data file shipped with cc:Mail: 1 116 552 bytes, md5 ea7119773ed2168897dc44ea5f8b53ca).
`ccmail/codepage.py` implements the single-byte conversion of §3.

Code page numbers used in cc:Mail messages and in CCINTL.TB:

| number | meaning |
|---|---|
| 437, 850, 851, 852, 857, 860, 861, 862, 863, 865, 866 | IBM/DOS code pages |
| 1250..1256 | Windows code pages |
| 1200 | Unicode (UTF-16LE), the pivot |
| 1201 | UTF-7 (base64 with `+`/`-`) |
| 1202 | UTF-8, BMP only, 1 to 3 bytes |
| 1203 | T.61 ("ISO-T61") |
| 1204 | EUC-TW, built from tables 1205..1208, prefix 0x8E 0xA2/0xAC/0xAD |
| 1205..1209 | multi-byte tables used by 1204 (CNS planes, inferred from that use) |
| 932, 936, 949, 950 | Shift-JIS, GBK/GB2312, Korean (KS C 5601), Big5 |
| 17316 (0x43A4) | a multi-byte table; identity not determined |
| 32768 (0x8000) | "MacScript0" = Mac Roman |
| 32769 (0x8001) | ISO-2022-JP, converted to/from 932 |
| 32770 (0x8002) | ISO-2022-KR, converted to/from 949 |

Classes:
- single-byte: 437, 850–852, 857, 860–863, 865, 866, 1250–1256, 32768, 34193–34201, 34374;
- multi-byte: 932, 936, 949, 950, 17316;
- "transformation" (an encoding of Unicode or of another code page): 1201–1204, 32769, 32770.

## 1. Header tags 0x20, 0x21, 0x31 (and 0x1D, 0x22)

### 1.1 Data length

Fixed data length per tag: 0x20, 0x21, 0x31 → 2 bytes (a little-endian word); 0x1D → 12; 0x22 → 8.

### 1.2 Meaning

| tag | value | describes |
|---|---|---|
| 0x31 | code page | **names** in the header: author (01), recipients, 0F/14 path names. Names are looked up in the directory in this code page |
| 0x20 | code page | **subject** (tag 05) |
| 0x21 | code page | **text of a text item** |
| 0x1D | 12 bytes | not a code page; copied from message to message. Captured value: `00 00 05 00 21 03 01 00 04 00 00 00` (word +4 = 0x0321 = 801). Field meanings not determined |
| 0x22 | 8 bytes | message id; the post office appends it if absent (`router-answer.md` §2.4). Not a code page |

Placement of 0x21 varies between writers. Both layouts occur:

- **per item**: right after the item's tag-07 entry, one per text item;
- **message-level**: one 0x21 before the 07 entries. A captured message made by IMPORT has the
  order `01 31 03 05 20 21 07(len 0) 1D 22`, with two tag-06 descriptors. Messages generated by
  the post office may have no 07 entry at all.

A reader looking for the per-item tag finds none in the message-level layout and falls back to
the post office code page.

### 1.3 Which messages carry them

| messages from | 0x31 | 0x20 / 0x21 |
|---|---|---|
| Remote 3.40B uploads | none | none (an upload capture has `01 03 05 07` only) |
| the post office, forwarding | not added, not changed | not added; the header is passed on as stored plus tag 0x22 |
| the post office, its own messages | — | the post office machine's locale code page (1252 if it has none). Receipts: 0x20 and 0x21. Non-delivery and PROFS error reports: 0x20 only. Connection reports: 0x21 only |
| the post office, ADE messages | — | 0x21 = the post office code page |
| R8 Windows clients, SMTP and POP3/IMAP gateways | always | as the writer sets them; receipt-like messages (inferred) carry 0x20 = the Windows ANSI code page and 0x21 = the original subject's code page |
| IMPORT 8.01 (DOS) | 850 in the captured message (from MSG1.IMP) | 850 | 

850 is IMPORT's documented default (its "/CODEPAGE/n" option, default 850).
Not determined: the DOS post office (Router 6.02 for DOS), the cc:Mail DOS 8 client and the
Mac/OS2 clients.

### 1.4 What readers do

- Nobody converts a body when it is **stored or forwarded**. A message keeps its writer's code
  page; each reader converts for display from the tags.
- A message without tags is read in the post office code page.
- The directory itself stores names in Unicode; a name in a message is interpreted in the code
  page of its message (tag 0x31) or, without the tag, of the post office.

## 2. How a client's code page is known

1. **Post office code page.** It is directory attribute 237 (class 0x2000000) of the post office
   entry (attribute 204 of object 40); 437 if 0 or unreadable.
   - Attributes 238 and 239 are two-character language and country codes. The language selects
     the CCINTL.TB collation tables.
   - The default is the code page of the computer the post office was created on. The allowed
     values are 437, 850, 851, 852, 857, 860, 861, 862, 863, 865, 866, 932, 936, 949, 950,
     1250–1256.
2. **Per message.** Tags 0x31/0x20/0x21 (§1). No per-user code page attribute exists in the
   directory as far as examined. Not determined: whether R8 DOS/Windows clients store one in a
   user profile.
3. **Session negotiation.** The B0/AE negotiation (`router-answer.md` §1.2.1, `negotiation.md`)
   has packet types 1, 6, 8, 18/22/23 (PO database value, attribute 305 = PO id), 19, 20 and 24.
   None of them carries a code page.
4. **DOS client display.** A DOS client shows text in the PC's active DOS code page and never
   sends it in a message or the session.

**Consequence for tagless messages (Remote 3.40B uploads):** readers use the post office code
page. The post office's own name lookups for a tagless message use the code page it is already
working in; which one that is, is not determined.

## 3. CCINTL.TB

### 3.1 Format

Header (132 bytes):

| off | value in file | meaning |
|---|---|---|
| 0 | 3 | major version; a file with major ≠ 3 is not usable |
| 2 | 4 | minor; ≤ 2 → no extended directories; ≥ 4 → extended locale directory present |
| 4 / 8 | 0x84 / 0x380 | translation directory, 14-byte entries (64) |
| 0x0C / 0x10 | 0x544 / 0x900 | locale (collation) directory, 32-byte entries (72) |
| 0x14 / 0x18 | 0xAA83A / 0x326 | 806-byte table; its use is not determined |
| 0x1C / 0x20 | 0xAAB60 / 0x39C | **best-fit table**, 231 × (word Unicode, word replacement) |
| 0x24 / 0x28 | 0x404 / 0x140 | extended translation directory, 20-byte entries (16) |
| 0x2C / 0x30 | 0xE44 / 0x72 | extended locale directory, 38-byte entries (3: ch, zh, ko) |

Translation entry (14 bytes): `type(2) offset(4) size(4) from_cp(2) to_cp(2)`. The extended entry
adds `suboffset(4) count(2)`. A table is found by the pair (from, to).

| type | direction | data |
|---|---|---|
| 1 | cp → 1200 | 256 × word Unicode (512 bytes) |
| 3 | 1200 → cp | 256 bytes: direct byte for U+0000..00FF, then `(size-256)/4` sorted pairs (word Unicode, word byte) |
| 2 / 4 | multi-byte cp → 1200 / 1200 → cp | blocks (932 has its own layout) |

Locale entries (type 0x8003): 2-letter language at +10, flags at +12 (variants 0..3), collation
data. Languages: en fr de no sv cs sl hr nl pl hu ro os es ee in ja ru; extended: ch zh ko.
They are for sorting and comparing, not for conversion.

### 3.2 Single-byte tables (all pairs X ↔ 1200)

TB offsets of the type-1 (decode) table; the type-3 (encode) table follows it. The last column
compares the table with Python's codec of the same name.

| cp | type 1 at | type 3 at, size | vs Python codec |
|---|---|---|---|
| 437 | 0x0EB6 | 0x10B6, 692 | = cp437 (0 diffs) |
| 850 | 0x16FA | 0x18FA, 520 | = cp850 (0 diffs) |
| 851 | 0x2216 | 0x2416, 780 | no Python codec (Greek DOS); use the TB table |
| 852 | 0x2722 | 0x2922, 724 | = cp852 |
| 857 | 0x2BF6 | 0x2DF6, 416 | cp857 except D5, E7, F2 → U+003F |
| 860 / 861 / 862 / 863 / 865 / 866 | 0x2F96 / 0x3442 / 0x3882 / 0x3D32 / 0x41E6 / 0x469A | +0x200 each | = Python (0 diffs each) |
| 1250 | 0x4B92 | 0x4D92, 588 | cp1250 except 80 81 83 88 90 98 → private use (80 = U+F89E, 83 = U+F869) |
| 1251 | 0x4FDE | 0x51DE, 720 | cp1251 except 88 98 → PUA |
| 1252 | 0x136A | 0x156A, 400 | cp1252 except 80 81 8D 8E 8F 90 9D 9E → PUA (0x80 = U+F89E, **no euro**; 0x8E/0x9E are PUA, not Ž/ž) |
| 1253..1256 | 0x54AE / 0x597A / 0x5D22 / 0x61C6 | +0x200 | cp125x with undefined (1996) positions → private use (U+F8xx) |
| 32768 Mac | 0x1B02 | 0x1D02, 516 | mac_roman except BD → U+2126, DB → U+00A4 |
| 34193 ISO-8859-1 | 0x1F06 | 0x2106, 272 | latin-1 except 0E 0F 1B 8E 8F → U+003F |
| 34194..34201 ISO-8859-2..9 | 0x692A, 0x6D16, 0x7096, 0x7466, 0x78DE, 0x7CCA, 0x811E, 0x849E | +0x200 | iso8859-n except 0E 0F 1B and 80–9F → U+003F; 34198/34200: unassigned also '?'; 34198 maps 0x30–0x39 to U+0660..0669 (Arabic digits) |
| 34374 US-ASCII | 0x6626 | 0x6826, 260 | 00–7F except 0E 0F 1B; 80–FF → '?' |
| 61 T.61 | 0x87C6 | 0x89C6, 796 | T.61 subset |

Multi-byte: 932 (type 2 0x8CE2/19032, type 4 0xD73A/37608), 17316 (0x16A22), and in the
extended directory 936, 949, 950 and 1205..1209 (TB+0x404 entries 0..15).

Every type-3 pair list is strictly sorted with unique keys (checked), so a binary search equals a
linear lookup there. Encode quirks: 1252 U+2022 → 0xB7 (so 0x95 does not round-trip); Mac
U+00B7 → 0xA5.

### 3.3 Conversion with the tables

The compatible conversion from code page `from` to code page `to`:

1. `from == to`, or either is 0 → copy unchanged. Transformation code pages and multi-byte code
   pages have their own converters.
2. Single-byte to single-byte goes through Unicode. The decode table gives U. Then the encode
   table: U < 0x100 → the direct byte, else binary-search the pairs (not found → '?').
3. If the result is '?' and U ≠ '?', look U up in the best-fit table:
   - found → **low byte only** of the replacement word;
   - not found → '?'.

   Examples: é→e, Ł→L, ‘’→', “”→", …→'.', Æ→'A', ß→'s', ©→'c', «→'<'. The table holds
   Latin-1, Latin Extended-A, U+0192 and general punctuation.
4. No table for the pair → the text is copied unchanged.

Caveat: the best-fit table is sorted except for one duplicate key (entries 224/225 are both
U+2032; the second should be 0x2033). A binary search on 0x2032/0x2033 may hit either one ('\''
or '"').

### 3.4 Internet code page map

Code page → internet charset, as used by compatible gateways (37 pairs). An unlisted code page
maps to itself.

| cp | → internet cp |
|---|---|
| 437 850 851 860 861 863 1252 0 32768 | 34193 ISO-8859-1 |
| 852 1250 | 34194 ISO-8859-2 |
| 865 | 34196 ISO-8859-4 |
| 866 1251 | 34197 ISO-8859-5 |
| 1256 | 34198 ISO-8859-6 |
| 1253 | 34199 ISO-8859-7 |
| 862 1255 | 34200 ISO-8859-8 |
| 857 1254 | 34201 ISO-8859-9 |
| 932 | 32769 ISO-2022-JP |
| 1200 | 1201 UTF-7 |
| 34193..34201, 34374, 32769, 32770, 1201, 1203, 1204 | themselves |

Internet charset → stored code page (6 pairs): 1201→1200, 1202→1200, 1203→34193, 32769→932,
32770→949, 1204→950.

## 4. Crossing post offices and the Internet

### 4.1 Between post offices

Header and body are sent as stored. Code page tags are not changed and text is not converted
(§1.3, §1.4). A message keeps its writer's code page. Each reader must convert.

### 4.2 Lotus SMTP gateway, outbound (observed)

- **Body text:** converted from the item code page (or, if 0, the gateway's configured code page)
  to the internet code page of §3.4, with §3.3 for unmappable characters.
- **Label:** 34193..34201 → "ISO-8859-1".."-9", encoded 7bit or QP by content. 34374 →
  "US-ASCII". 32769 → "ISO-2022-JP", 7bit. 949/32770 → "ISO-2022-KR" (7bit) or "EUC-KR" (base64).
  936 → "GB2312", base64. 950 → "Big5", base64. Anything else → "ISO-8859-1".
- **Subject:** bytes **not converted**. 850, 437 and 1252 are labelled "US-ASCII"; 34193..34201 →
  ISO-8859-n; 932/32769 → "ISO-2022-JP"; others → "US-ASCII". RFC 1522 Q-encoding if any byte is
  ≥ 0x80, B-encoding for 932. So an 850 subject leaves as `=?US-ASCII?Q?` with raw 850 bytes.

### 4.3 Lotus SMTP gateway, inbound (observed)

- **Charset → code page:** US-ASCII → 850; ISO-8859-1..9 → 34193..34201; ISO-2022-JP → 32769;
  GB2312 group → 936; EUC-KR group → 949; ISO-2022-KR → 32770; Big5 group → 950; EUC-TW group →
  1204; ISO-T61 → 1203; UTF-7 → 1201; UTF-8 → 1202. Unknown names get 850, and so do
  **Windows-125x, KOI8-R and anything else not in this list**.
- **Conversion:** only transformation code pages are converted: UTF-8/UTF-7 → **1200** (Unicode
  text items), ISO-2022-JP → 932, and so on. Everything else is stored **unconverted** and tagged
  with that code page: ISO-8859-1 text is stored with tag 0x21 = 34193. Unknown charsets are
  stored raw and labelled 850. A part with no charset gets the gateway's configured code page,
  with no conversion (`smtp-link.md` §3).
- **Subject:** RFC 1522 decoded and cut at 60 bytes, tagged with 0x20 (`smtp-link.md` §3). Not
  determined: which code page a decoded encoded word is tagged with.

### 4.4 POP3 and IMAP (R8.1, from `pop3-imap.md`)

- **POP3:** converts like the outbound SMTP gateway (item code page; post office code page if 0;
  §3.4).
- **IMAP:** does not convert. Its labels map 850 and 437 to US-ASCII.

## 5. Recipe for our server

Our clients are Remote 3.40B (no tags, display in the PC's DOS code page). Other cc:Mail readers
convert per message from the tags. So:

1. **Configuration.**
   - `po.codepage`, default **437** (the default when attribute 237 is empty). 850 matches
     IMPORT's default and the tags in our capture, but attribute 237 of our sample PO is not
     determined (§6.6).
   - `user.codepage` per user, default `po.codepage`. It is the DOS code page of that user's PC.
     The protocol gives no way to learn it (§2.3–2.4).
2. **Code page of an incoming (uploaded) message:**
   - names and subject: 0x31 / 0x20 if present, else the uploader's `user.codepage`;
   - text items: the 0x21 after the item's 07, else the first 0x21 in the header, else 0x31,
     else `user.codepage`. The 0x31 step is our choice; other readers fall back to the post
     office code page.

   Store the bytes raw. Store the code page as tags: add 0x31 after 01 and 0x20/0x21 after 05,
   matching IMPORT's layout (`01 31 03… 05 20 21 07…`). Do not convert on storage; cc:Mail does
   not either.
3. **Download to a Remote user:** convert names, subject and text from the message code page
   to `user.codepage` with the CCINTL.TB tables (§3.3, including best fit). If the code pages
   are equal, or the message code page is 0, send as is. After converting, **rewrite
   0x31/0x20/0x21 to `user.codepage`**. Remote stores tags and forwards them unchanged
   (`session-layer.md` §4.3), so stale tags would come back on forwarded mail.
4. **Gateway outbound (to UTF-8 / MIME):** decode with the type-1 table of the message code
   page.
   - Private-use results U+F8xx (undefined 125x bytes) and the Mac quirks stay as the table
     gives them. Map them to U+FFFD. A conversion to ISO-8859-1 with the tables turns them into
     '?' (encoding U+F89E to 34193 gives 0x3F).
   - Compatible output is the §3.4 target (850 → ISO-8859-1, and so on), with '?' or best fit
     for characters outside it.
   - Better and still readable: emit `charset=utf-8` (no loss). The Lotus SMTP gateway would
     have lost characters outside the ISO set.
   - Subject: RFC 2047 B or Q with the real charset. Do not copy the US-ASCII mislabelling of
     §4.2.
5. **Gateway inbound:** decode any charset Python knows, including those the Lotus gateway does
   not (Windows-125x, KOI8-R, UTF-8), plus RFC 2047 words, into Unicode. Then encode to the
   recipient's `user.codepage` with §3.3: encode table, else best-fit low byte, else '?'. Write
   tags 0x31/0x20/0x21 = that code page.
   - The Lotus gateway would store ISO-8859-x raw with tag 34193.., and UTF-8 as 1200, both
     unreadable on Remote. We differ on purpose.
6. **Tables to support:** load them from CCINTL.TB at the offsets in §3.2 (from the user's PO
   files or a converted copy). Do not use Python codecs; only 437, 850, 852, 860–863, 865 and 866
   match exactly.
   - Must have: 437, 850, 851, 852, 857, 860, 861, 862, 863, 865, 866 (DOS clients), 1250–1256,
     34193–34201, 34374, 32768.
   - Optional: 932/936/949/950. For these Python's cp932/gbk/cp949/cp950 are only approximate,
     with no measured equivalence.
   - Unmappable on encode: exactly §3.3 (the table's direct byte or pair, then the best-fit low
     byte, then '?').

## 5a. Additions in our server (not in cc:Mail)

- **1125 (CP866U, RUSCII, Ukrainian RST 2018-91)** is not in CCINTL.TB (its code page list:
  61, 437, 850, 851, 852, 857, 860-863, 865, 866, 932, 1200, 1250-1256, 17316, 32768,
  34193-34201, 34374). Our table comes from CPython's `Lib/encodings/cp1125.py` (PSF license).
  It equals the 866 table at 80..EF and differs at F2..F9 (866: Є є Ї ї Ў ў ° ∙; 1125:
  Ґ ґ Є є І і Ї ї). A reader using the 866 table shows F2..F9 of 1125 text as the wrong letters.
  Accepted names in po.json: 1125, "866u", "cp866u", "ruscii", "cp866nav".
- Internet mapping for 1125: ISO-8859-5 like 866 (it lacks і/ї/є/ґ), but our gateway emits
  UTF-8 whenever ISO-8859-1 does not hold the text, so nothing is lost.
